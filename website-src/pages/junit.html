JUnit5 Test Suite (§6 and §7)

Assignment §6 requires "a JUnit5 test suite for the complete library." §7 requires we evaluate its quality by line coverage, branch coverage, mutation score, test count, assertion count, and execution time, plus a discussion of readability and flakiness.

What we built

180 unit tests across 13 test classes covering every public class in dk.brics.automaton.*. Most were AI-drafted and then reviewed / adjusted; the PICT, metamorphic, differential, and infra suites on top bring the total to 1948.

Mutation score (PIT 1.17.0)

Full 1948-test suite: 56.8% mutation detection rate (1058 of 1862 mutations killed or timed-out). Test strength: 70%.

We report detection rate (killed + timed-out) rather than raw kill count because timeouts are also a real detection signal — PIT halted because the mutant made a test hang, which means the test noticed something wrong. Detailed per-class breakdown and 5-mutant analysis on the design page and in docs/mutation-analysis.md.

558 source-level assertion statements understates the real number of checks performed, because several of them run inside a loop over parameterized rows or sampled inputs rather than once. The clearest example: PictMetamorphicTest has 5 assertion statements in its source, but each runs once per property (5) per sampled input (5) per PICT row (754 across 2/3/4-wise) — 18,850 runtime assertion evaluations from 5 lines of source (see Metamorphic Testing). Adding PictRegexTest's ~1,500 and the infra suite's CSV-driven invocations, the full suite evaluates well over 20,000 assertions despite having under 600 assertion statements in source. Both numbers are worth reporting: source count reflects how much test logic a human has to read and maintain; runtime count reflects how much of BRICS' behaviour actually gets checked on every run.

Both timings are fast (single-digit seconds) because BRICS' automata operations are pure, in-memory, and small at the sizes our regexes generate — there's no I/O, no network, no sleeps. That headroom is what makes the 6 separate per-strength PIT runs on the CIT page practical to run repeatedly during development.

Readability, debugging, and redundancy

Readability. Every hand-written test class uses @Nested to group related cases and @DisplayName on both the nested class and the method, so a failure report reads as a sentence (e.g. "Resource lookup > exists throws NPE for missing resources (BRICS bug — should return false)") rather than a bare method name. The PICT-driven and infra tests go further: each @ParameterizedTest name template embeds the row's actual parameter values ("2-wise[{index}] {0}/{1}/{2}/{3}/{4}/{5}/{6}" in PictRegexTest), so a failing row is identifiable from the test name alone, before opening a stack trace.

Ease of debugging failures. Every assertion in the PICT and metamorphic suites carries a lazy failure-message supplier that reconstructs the exact regex, operation, and input that failed (e.g. "Row failed to compile: " + row.regex() in PictRegexTest, or "MR-A double-complement mismatch: regex=" + row.regex() + " input=" + describe(s) in PictMetamorphicTest). Because RegexRowBuilder.build() is a pure, deterministic function of its row inputs, any failure is reproducible by re-running that one parameterized invocation in an IDE — no need to re-run the whole suite or guess at hidden state.

Redundancy. The PICT-driven suites are the honest exception here, and we say so rather than hide it: many of the 754 rows differ in only one parameter, so they exercise overlapping code paths. That's the mechanism behind the flat mutation-score curve documented on the CIT page — 3-wise (152 rows) already catches almost everything 4-wise (568 rows, 3.7× the rows) catches, which is direct evidence that a large share of the 4-wise rows are redundant for fault-detection purposes even though PICT guarantees no two rows are redundant for coverage purposes (every quadruple of parameter values is still covered exactly once). Coverage-redundancy and fault-detection-redundancy are different things, and CIT only optimizes the former. RegexRowBuilder.alternated() also deliberately reuses the same term for every alternation branch (see its source comment) — a further source of redundant-looking rows that is in fact intentional, to exercise BRICS' union-of-equal-branches minimization path specifically.

Flaky behavior

None observed. The suite has no Thread.sleep, unseeded Random, wall-clock reads, or network/file I/O in its test code — every input is either hand-written, derived deterministically from a PICT CSV row via RegexRowBuilder (see RegexRowBuilderInfraTest's determinism check), or a fixed literal. All 1950 tests passed on every one of the repeated local runs performed while preparing this report. The one source of non-determinism in this project is PIT's own mutant-timeout classification during mutation testing, not the JUnit5 suite itself — see I-3 in Threats to Validity.

Bugs found while writing tests (not by mutation testing)

Three real BRICS defects were surfaced by coverage-guided test writing — PIT would not have found them because mutation testing evaluates the suite against the code as written, not the code itself. All three became formal refactoring proposals in §12.

  1. Datatypes.exists() throws NPE for missing resources instead of returning false.
  2. isTotal() is a structural predicate masquerading as a semantic one.
  3. SpecialOperations.getFiniteStrings(a, limit) silently returns null on overflow.
