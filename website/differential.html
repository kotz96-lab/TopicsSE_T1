Differential Testing (§11)

Assignment §11 requires comparing selected BRICS behaviours against java.util.regex to identify semantic differences, edge cases, and possible bugs.

Test design

Two regex dialects, whole-string match on both sides. We test ~38 patterns from the compatible subset (features both dialects support: literals, ranges, negation, alternation, quantifiers, grouping) and document known semantic divergences separately.

Source: DifferentialTest.java.

Documented disagreements

Three genuine dialect divergences we found. Each is a captured test in the "KnownDisagreements" nested class.

1. Dot metacharacter and newline

BRICS treats . as "any character including newline." Java's default treats . as "any character except line terminator." So "." vs input "\n": BRICS matches but Java does not.

2. The @ character — BRICS' ANYSTRING metacharacter

In BRICS' default regex flags, @ means ANYSTRING (matches any string, including the empty string). Java treats @ as a literal character.

Concrete example: pattern [a-z]+@[a-z]+ against input "abc": BRICS matches (it parses as "letters, then anything, then letters" — with the "anything" matching the empty string between position 1 and position 1) but Java does not (it requires a literal @ in the input).

Anyone porting a regex from Java to BRICS (or vice versa) without knowing about this metacharacter gets silently wrong matching. No error, no warning — just different accept/reject decisions.

3. The # character — BRICS' EMPTY metacharacter

In BRICS, # means the EMPTY language (matches nothing at all). In Java, # is a literal. Pattern # vs input "#": BRICS rejects (empty language accepts nothing) but Java matches (literal # character).

BRICS-only operators (no equivalent in Java)

Three regex operators BRICS supports that java.util.regex doesn't. We show explicit differential comparisons for each.

  • & (intersection): BRICS (a|b)&(b|c) matches only "b". Java parses the same source as capture group, literal &, capture group — matches "a&b", "b&c", etc. The same string is accepted by exactly one engine at a time.
  • ~ (complement): BRICS ~(a) matches everything except "a". Java parses it as literal ~ followed by capture group (a), so it matches only the 2-character string "~a".
  • <name> (automaton reference): BRICS looks up a named automaton via AutomatonProvider. Java parses the angle brackets as literals.

Finding — and its implication for the report

The @, #, ~, &, and <> metacharacters together mean that five ordinary ASCII characters have different meanings in BRICS vs every other mainstream regex engine. This surfaces as Refactoring Proposal 4 in the design section: BRICS' default regex flags should be literal-first, with the metacharacter interpretations opt-in via explicit syntax flags.

We discovered the @ metacharacter behaviour accidentally — a differential test that we initially intended as "compatible subset" ([a-z]+@[a-z]+) failed because BRICS accepted "abc". That's a concrete example of differential testing surfacing a real finding.
