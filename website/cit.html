Combinatorial Interaction Testing (§9)

This is the single largest chunk of the assignment (25 points). We use Microsoft PICT v3.7.4 to generate test inputs at 2-wise, 3-wise, and 4-wise interaction strengths, and integrate them into JUnit5 via @ParameterizedTest+@CsvFileSource.

The idea in one paragraph

Our BRICS regex-construction pipeline has 7 configurable parameters (character alphabet, quantifier, alternation depth, nesting depth, etc.). Fully cross-multiplying gives 12,960 configurations — too many to test. PICT reduces this by producing a small table where every pair of parameter values appears together at least once (2-wise), or every triple (3-wise), or every quadruple (4-wise). Reductions:

Interaction strengthPICT rowsvs full 12,960
2-wise (pairwise) 34 99.7% smaller
3-wise 152 98.8% smaller
4-wise 568 95.6% smaller

The model

pict/models/regex.pict has 7 parameters and 4 constraints: 

Alphabet:         ascii_lower, ascii_alnum, unicode_bmp, single_char
CharClassKind:    single, range, set, negated
Quantifier:       none, star, plus, optional, bounded
AlternationDepth: 0, 1, 2
NestingDepth:     0, 1, 2
Operation:        toAutomaton, determinize, minimize, complement, union, intersection
InputLength:      empty, short, medium

# Constraints
IF [Alphabet] = "single_char" THEN [CharClassKind] IN {"single", "set"};
IF [Alphabet] = "single_char" THEN [AlternationDepth] IN {0, 1};
IF [CharClassKind] = "negated" THEN [Alphabet] <> "single_char";
IF [NestingDepth] = 2 AND [AlternationDepth] = 0 THEN [Quantifier] <> "none";

Full parameter-by-parameter rationale (why these values, what BRICS code paths each targets, why we excluded surrogate pairs / control characters / anchors) in docs/pict-rationale.md.

Integration — how each PICT row becomes a test

RegexRowBuilder.java deterministically maps a row of abstract parameter values to a concrete BRICS regex string plus a test input. Same row always produces the same regex — reproducibility guaranteed.

Two consumer test classes drive the rows through PIT:

  • PictRegexTest — weak oracle: per row, asserts (a) pipeline compiles and runs without throwing, and (b) A.complement().complement().run(input) == A.run(input) on one input.
  • PictMetamorphicTest — strong oracle: per row, asserts five metamorphic properties (double complement, union/intersection idempotence, minimize preserves, determinize preserves) on five sampled inputs. 25 assertions per PICT row.

Direct answer to RQ2 — the headline experiment

Research Question 2: Does combinatorial interaction testing improve mutation scores?

Answer: it depends on the oracle. With a weak oracle, interaction strength does not measurably help. With a strong oracle it does — up to 3-wise, then plateaus. And the gap between weak and strong oracles widens as strength grows, so the two dimensions compound.

The 3×2 grid — mutation kills

Each cell is the mutation-killing power of one strength × oracle combination in isolation (PIT filtered by JUnit tag via PIT's -DincludedGroups= flag — see the AI Tools page for the story of how we caught the filter bug).

Weak (smoke + double-neg, 1 input) 194 killed (9.6%) 205 killed (10.1%) 204 killed (10.0%)
Strong (5 metamorphic props, 5 inputs) 209 (10.3%) 229 (11.3%) 231 (11.4%)

Oracle 2-wise 3-wise 4-wise
Weak 40.8% 42.5% 42.1%
Strong 43.5% 47.6% 48.0%

Why the absolute numbers look small (~10%)

These runs are deliberately isolated — each is only 34-568 tests against 2087 mutations across 25 BRICS classes. About 76% of the mutations get NO_COVERAGE because the isolated PICT suite doesn't touch classes like Datatypes, AutomatonMatcher, or StringUnionOperations. When run together with the 180 hand tests, the full suite hits 51% mutation score.

Interpretation, in prose

Direction 1: effect of increasing interaction strength

TransitionWeak ΔStrong Δ
2-wise → 3-wise +11 kills +20 kills
3-wise → 4-wise −1 (noise) +2 kills (diminishing)

With the weak oracle, interaction strength is essentially flat. With the strong oracle, there's a real jump from 2 to 3-wise and then diminishing returns to 4-wise. Classic pattern — 3-wise catches most of what higher strengths would.

Direction 2: effect of strengthening the oracle

StrengthWeak → Strong Δ
2-wise +15 kills
3-wise +24 kills
4-wise +27 kills

The gap widens as interaction strength grows. Meaning the two dimensions compound — more combinations give the stronger oracle more scenarios in which to fire; more oracle sensitivity lets the extra combinations pay off. Neither dimension alone is worth much; together they add up.

Practical recommendations from this data

  1. Use at least 3-wise, not 2-wise. The +20 strong-oracle gain justifies +118 extra rows (~50 s of test time).
  2. Don't invest in 4-wise unless the oracle is very sensitive. Returns diminish; rows quadruple.
  3. Oracle strength > interaction strength. Strong × 3-wise (229 kills) beats weak × 4-wise (204 kills) despite 4-wise having almost 4× the rows.
  4. Combine both. The strong 3-wise sweet spot kills 229 mutants in ~9 min — excellent per-second yield.

Reproducing the CIT experiment

# Regenerate PICT tables (needs tools/pict.exe or pict on PATH)
pwsh scripts/generate-pict.ps1

# Individual per-strength PIT runs — each ~2-20 minutes
./mvnw -Ppit test -DincludedGroups=pict-2wise         # weak,   2-wise
./mvnw -Ppit test -DincludedGroups=pict-3wise         # weak,   3-wise
./mvnw -Ppit test -DincludedGroups=pict-4wise         # weak,   4-wise
./mvnw -Ppit test -DincludedGroups=pict-strong-2wise  # strong, 2-wise
./mvnw -Ppit test -DincludedGroups=pict-strong-3wise  # strong, 3-wise
./mvnw -Ppit test -DincludedGroups=pict-strong-4wise  # strong, 4-wise
Careful: -Dgroups= is a Surefire flag; PIT ignores it. Use -DincludedGroups=. An earlier version of this experiment used the wrong flag and produced apparently-valid but scientifically-meaningless results; see the AI Tools page for the correction story.
