Software Design Evaluation (§12)

§12 asks for SOLID analysis, design-pattern identification, and ≥3 concrete refactoring proposals. We deliver a principle-by-principle review, a design-pattern catalogue, and 4 formal refactoring proposals (three defects/API issues plus one interoperability recommendation).

SOLID — principle by principle

S — Single Responsibility

Partially violated. The most impactful violation is that Automaton.java (~1150 lines, 78 public methods) is simultaneously:

  1. a data structure (holds initial, singleton, deterministic fields; is a mutable graph of State and Transition);
  2. a facade for every operation (most of those 78 methods are one-line delegates to BasicOperations, MinimizationOperations, SpecialOperations, ShuffleOperations);
  3. a static factory (makeEmpty, makeString, makeChar, ...);
  4. a serialization endpoint (load, store, custom equals/hashCode);
  5. and a global-configuration container (setMinimization, setMinimizeAlways, setAllowMutate — static flags affecting the whole library).

Each is a distinct responsibility. Any of them changing touches Automaton.java.

O — Open / Closed

Violated. The principle says "open to extension, closed to modification" — you should be able to add new features by writing new code rather than editing existing files. BRICS has almost no interfaces or abstract classes in the automaton module (except Java's marker interfaces Serializable and Cloneable). The one seam is AutomatonProvider for named-automaton lookup. To add a new operation you must modify Automaton.java and one of the utility classes. To swap minimization algorithms you edit MinimizationOperations.minimize's switch statement.

L — Liskov Substitution

Mostly vacuous, one genuine hazard. BRICS uses inheritance in almost no places. The one hazard is Automaton.isTotal() — its method name promises a semantic query but its implementation is a purely structural check. Not an LSP violation in the classic class-hierarchy sense (there's no subclass), but a violation of the "contract vs behaviour" flavour.

I — Interface Segregation

Vacuously satisfied. No domain interfaces to segregate. The one interface (AutomatonProvider) is a single-method interface — textbook ISP compliance.

D — Dependency Inversion

Violated systematically, but with a caveat. Every dependency in BRICS is concrete: BasicOperations.union(Automaton a1, Automaton a2) — no interface, callers can't substitute alternatives. RegExp depends directly on Automaton, BasicAutomata, BasicOperations.

Fair caveat: BRICS is a library, not an application. In library code, concrete types in signatures are often justifiable — there's typically no substitution concern (nobody's swapping in an alternative Automaton), and interface indirection would add ceremony without benefit. Read the DIP verdict as "opinionated" rather than "broken."

Design patterns actually used

Static factory method (widely used)

Where: BasicAutomata.make*, Automaton.make*. Intent-revealing names (makeAnyChar vs new Automaton()) and hidden singleton short-circuits. Downside: contributes to the god-class problem on Automaton.

Utility class / static-method module (widely used)

Where: BasicOperations, MinimizationOperations, SpecialOperations, ShuffleOperations are all final classes with private constructors and static methods only. Advantage: easy testability, no lifecycle. Downside: locks in the OCP violation.

Comparator (small)

TransitionComparator implements Comparator<Transition> exposes two orderings via a constructor flag. Minor code smell — would be cleaner as two named comparators.

Visitor-adjacent recursive walk

RegExp.toAutomaton recurses over the parse tree by switching on a Kind enum. Not full Visitor (no accept method), but same intent: separate parse-tree structure from transformation. Suffers the classic switch-over-type-tag OCP issue.

Refactoring proposals

Proposal 1 — Fix Datatypes.exists() to actually return false

Type: Bug fix   Location: dk.brics.automaton.Datatypes line 470

Problem. Current implementation:

public static boolean exists(String name) {
    try {
        Datatypes.class.getClassLoader().getResource(name + ".aut").openStream().close();
    } catch (IOException e) {
        return false;
    }
    return true;
}

ClassLoader.getResource(...) returns null when the resource is absent from the classpath. Calling .openStream() on null throws NullPointerException, which is not an IOException — so it escapes the catch. exists("NoSuchName") throws NPE instead of returning false.

Proposed fix:

public static boolean exists(String name) {
    URL url = Datatypes.class.getClassLoader().getResource(name + ".aut");
    if (url == null) return false;
    try (InputStream in = url.openStream()) {
        return true;
    } catch (IOException e) {
        return false;
    }
}

Fixes the NPE and the stream leak on the happy path.

Effort: low. Risk: low (any caller already wrapping exists in defensive NPE-catch will get false instead — the intended behaviour).

Proposal 2 — Clarify isTotal(): semantic vs structural

Type: API-clarity refactor   Location: BasicOperations.isTotal line 583, delegate at Automaton.isTotal line 943

Problem. isTotal() reads like a semantic query ("does this automaton accept every string?"). Actually it's a structural check: returns true only if the initial state accepts AND has exactly one self-loop from MIN_VALUE to MAX_VALUE. Any semantically-total automaton in a different shape returns false. Concrete surprise: complement(makeEmpty()).isTotal() == false even though the resulting language IS Σ*.

Two fix options:

  • Option A (surgical): rename to isCanonicalTotal(). Its actual semantics become explicit in the name. Zero cost, mild breaking change.
  • Option B (compatible): keep the fast path, add a semantic fallback via subsetOf(makeAnyString(), a) when the canonical shape doesn't match. Costs one subsetOf call in the slow path.

Proposal 3 — Replace getFiniteStrings(a, limit) null-return

Type: API-hygiene refactor   Location: SpecialOperations.getFiniteStrings line 493

Problem. When the language has more than limit strings, the method silently returns null — but the return type is Set<String>, so naive callers who write for (String s : result) { ... } get an NPE.

Two fix options: either throw IllegalStateException ("language has more than N strings"), or change the return type to Optional<Set<String>>. Both make the "too many strings" signal explicit at the call site.

Proposal 4 — Make BRICS' regex default flags conservative (literal-first)

Type: API-default choice (interop)   Location: RegExp constructor line 188

Problem. By defaulting to ALL, BRICS silently gives five ordinary ASCII characters non-obvious meanings:

CharBRICS meaningJava / PCRE / POSIX meaning
@ ANYSTRING (Σ*) literal @
# EMPTY (matches nothing) literal #
~ complement of following expression literal ~
& intersection of two expressions literal &
<name>automaton reference literals

Anyone porting a regex between BRICS and Java gets silently wrong matching — no crash, no warning, just different accept/reject decisions on the same input. Reproducer: the @-metacharacter finding on the differential page.

Proposed fix: flip the default. new RegExp(s) should delegate to new RegExp(s, RegExp.NONE) — all five metacharacters literal by default. Users opt in with new RegExp(s, RegExp.ANYSTRING).

Effort: low. Risk: high — breaking change for every existing user relying on the default flags. Could be phased with deprecation across two releases.

5-mutant analysis (§8)

§8 additionally requires analysis of ≥5 surviving mutants from the PIT run. Detailed analysis in docs/mutation-analysis.md. Summary of the five patterns we identified:

  1. Behavioural-oracle blindness: mutants change internal state (a determinism flag, a minimize call) without affecting the language. Language-membership tests are blind. Example: BasicOperations.concatenate line 60.
  2. Behavioural-oracle blindness (structural): mutants remove an idempotent optimization (like a skipped minimize() call). Result has bloated state count but same language. Example: RegExp.toAutomaton line 326.
  3. Boundary blindness at character-range extremes: our test inputs use friendly ASCII, so mutants at Character.MAX_VALUE boundaries slip through. Example: Automaton.getStartPoints line 410.
  4. Off-by-one in private helpers reachable only via limited public API: mutating (char)(c+1) to (char)(c-1) in BasicAutomata.atLeast line 158 doesn't fail our two makeInterval tests because they don't sample every boundary value.
  5. Output-content blindness: our toString tests only assert non-null; mutations that scramble the string but still return non-null survive. Example: Transition.appendCharString line 136.

Only one of the five is behaviourally equivalent under our current oracle (the minimize-skip mutant). The other four are killable with targeted extra assertions — typically one or two new test methods each.
